# ORG-TRADE-1 — CPU Trade Style Within Fairness Bounds

## Objective

Let CPU organization identity influence whom clubs target, protect, and package in trades while preserving existing fairness, exploit prevention, budgets, and information limits.

## Source-first checkpoint

Map trade valuation, needs, negotiation, prospect protection, timeline/contend state, fairness floors, tests, and module boundaries. Establish regression scenarios before edits.

## Design

- Identity may adjust target selection, willingness, package composition, patience, and prospect protection within bounded ranges.
- It may not lower the fairness floor, grant true-talent visibility, create assets, ignore contracts/budgets, or accept objectively invalid deals.
- Keep organization identity separate from baseline market value.
- Refactor only a narrow seam needed for safe injection; if the module cannot accept the change safely, split a prerequisite refactor goal rather than bundling it.

## Proof

- existing fairness/exploit suite remains green;
- no hidden information or value creation;
- constructed profiles produce different reasonable targets/packages;
- same-seed reproducibility;
- multi-season trade-frequency and asset-balance soak;
- full gates.

## Scope cut line

Trade domain only. No development, FA/payroll, broad trade rewrite, new negotiation UI, or schema work unless a factual decision ledger is already established and truly needed.

## Done

CPU trade behavior is recognizable and fair, with no regression in trade exploits or deterministic behavior.
